/implement control flow map

How the implement skill moves from a spec or a set of tickets to a merged-ready Pull Request: who acts at each step, where the flow branches or loops, and what bounds each loop. Source: skills/implement/SKILL.md and its references/.

User

Starts the session, confirms seams, answers the questions that are theirs to decide, reviews the PR, picks follow-ups.

Orchestrator

The session that ran the skill. Plans, talks to the user, dispatches sub-agents, reads their reports. Never edits source or runs tests.

Sub-agents

Do everything that reads widely or prints a lot. One writer at a time in the shared worktree. Each reads the plan file first and replies with a short report.

Select any box to see what happens there. The flow runs top to bottom; after every dispatch the orchestrator ends its turn and the sub-agent's report re-invokes it.

Step reference

The report protocol

Every sub-agent except the explore agent and the adversary replies with the same report of at most 15 lines. Its status line is what the orchestrator branches on.

StatusMeaningWhat the orchestrator does next
doneWork is green and committed.Moves to the next seam, or the next step.
partialA seam agent stopped at a green checkpoint after about 40 turns, to keep its context small.Dispatches a fresh seam agent for the same seam. The plan's seam line says what is left.
needs-decisionThe work would change a confirmed seam or a public interface, add a dependency, or hit a disputed reading of the spec.Puts the question to the user, records the answer under Decisions, then resumes the same agent with SendMessage, or dispatches a fresh one if it is gone.
blockedThe agent cannot go on: missing infrastructure, or still red after its allowed rounds.Decides the next step with the user. Never starts the next seam on top of a broken one.

The whole quality gate runs twice and the full test suite exactly once. Everything in between runs only the tests in scope, so no agent pays for the full suite on a branch that is still changing.

State and guards

The plan file is the session's memory

.implement/plan.md is the durable state and the first thing every sub-agent reads (the adversary never sees it). After a context compaction the orchestrator re-reads it instead of asking anyone again. It is excluded from commits through info/exclude.

SectionHoldsWritten by
SpecTickets or spec pathOrchestrator
CommandsExact test, typecheck, lint, full suite commands; what CI pinsOrchestrator from the explore report; any agent corrects a wrong line
MapAt most 10 lines of paths to touch or imitateOrchestrator from the explore report
SeamsKind, mode, assigned tests, statusOrchestrator; the working agent sets the status
DecisionsUser answers, assumptions marked assumed, choices later agents must honourOrchestrator and agents, one line each

Guards that hold for the whole session

  • Commit guard. A PreToolUse hook on Bash (scripts/block-commit-on-main.sh) blocks git commit and git push on main or master, and any push that targets either. If the script cannot be found it fails closed. Sub-agents may not inherit the hook, so each brief has them check the branch before every commit.
  • Only the orchestrator pushes. Sub-agents commit once green and never push.
  • Worktree shell rules. Heredocs, command substitution, shell variables, and loops are refused. Files are written with the Write and Edit tools; && and pipes are fine.
  • Tests only at confirmed seams. An agent that finds a seam is wrong stops with needs-decision; it does not invent one.
  • Ask early, ask together. Questions that are the user's (seams, scope, public interface, new dependency, an ambiguous spec line) are collected before the first seam. Everything else the orchestrator decides, records as assumed, and lists in the PR.
  • Independent adversary. It gets its own brief with only the spec, the diff, and the existing tests, so it cannot inherit the builder's reasoning.

Without a sub-agent tool

The same flow runs inline, in the same order, with the same plan file, and each role line becomes the checklist for its step. The adversary and the review can no longer run together: the review runs after the adversary, both are fixed in step 8, and the adversary's result is flagged as not independent.
